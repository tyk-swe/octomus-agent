GOOD CHANGES HAVE A PAPER TRAIL

From “this could be better”
to “take a look at this.”

Give Octomus a repository and boundaries. It does the exploring, building, and checking. You keep the final say.

  1. 01

    Find the worthwhile work.

    Discovery agents explore your code, project instructions, history, and existing PR context for concrete improvements.

    Grounded in your repository
  2. 02

    Give every idea a second look.

    Two independent reviewers challenge proposals. The orchestrator records why each is accepted, deferred, or rejected.

    Doing nothing is a valid outcome
  3. 03

    Build it. Review it. Check it.

    Accepted work gets an isolated checkout, fresh reviews of the full diff, and your configured verification commands.

    Checks must pass on the reviewed revision
  4. 04

    A PR, ready for you.

    Octomus publishes the change with its evidence. Read the diff, ask for more work, and choose what deserves to merge.

    Merging stays with you

A FEW GOOD QUESTIONS

Before you
dive in.

✳
How is this different from giving an AI a task?

Octomus discovers the work as well as executing it. It reads repository context, asks two reviewers to challenge the proposals, and may reject every idea. Accepted work goes through code review and your verification policy before publication.

Does it merge or deploy my changes?

No. Octomus delivers GitHub pull requests. You decide what to merge, deploy, or migrate. Pause stops new work; active tasks can still finish and publish. Individual tasks can be cancelled.

What does it cost?

You provide the VM and Codex or OpenCode provider access. Their costs depend on your setup and usage. Octomus’s session-admission budget is an operating limit, not a dollar cap. Validated per-task and daily cost figures are not available yet.

Can I run it on my laptop?

The supported operating model uses a dedicated Ubuntu 24.04 VM with no unrelated credentials. Repository instructions and commands run with the service user’s permissions. Keep the private dashboard on loopback and access it through SSH forwarding. Read the threat model before setup.

Is the demo a real run?

No. The public walkthrough and screenshots use deliberately synthetic data. They show the interface and decision process, including failures. They are not evidence of real delivery, reliability, speed, or savings.

Where can I ask questions or report a bug?

Use GitHub issues for feedback and reproducible bugs. Please leave tokens and private repository data out of reports. For vulnerabilities, follow the security policy.
