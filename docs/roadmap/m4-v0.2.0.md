# M4 — v0.2.0

[Roadmap](README.md) · **Depends on:** [M2](m2-state-upgrades.md),
[M3](m3-ci-coverage.md) · **Release depends on:** [M1](m1-release-v0.1.0.md) ·
**Target:** Fri 2026-11-13

## Why

At planning time, three features from the Rust implementation had not been ported
to Go. They sit on
the unmerged `origin/claude/feature-additions-discussion-8y1939` branch, which
changes Rust code and cannot be merged:

- **Webhooks.** v0.1.0's `internal/notifications` sent only blocked-task and error-pause
  notices; the branch also had published-task, failed-cycle and audit events.
- **Planning inputs.** The owned pull-request record (`PullRequest` in
  `internal/model/types.go`) carried no review state, CI status or
  mergeability. Comments are read only to find the task marker
  (`internal/git/github.go`).
- **Rebasing.** A moved default branch could be rebased onto. This one stays out
  of this horizon (see [the roadmap](README.md#not-in-this-horizon)).

v0.2.0 is also the first release whose upgrade runs on real v0.1.0 state, so it
tests M2 outside the test suite.

## Deliverable

A `v0.2.0` release with richer notification events and owned-PR review and CI
context in planning. It opens and migrates v0.1.0 state, and its upgrade is
rehearsed and recorded.

## Committed scope

1. **Notification events** for a published task, a failed planning cycle and a
   completed audit. They go through the existing outbox and opt-in webhook, with
   the same redaction, bounded backlog and retry behavior as today
   ([deployment](../deployment.md)).
   - The outbox is filled by triggers in `internal/store/schema.sql`, so these
     events are a schema change and the first real M2 migration.
2. **Owned-PR context in grounding.** Each owned pull request gains review
   decision, CI check status and mergeability.
   - Read them in `internal/git/github.go`, carry them in the PR record and show
     them to planning prompts.
   - Keep the context bounded and source-attributed, like the existing
     contributor and fork context.
   - External pull requests stay read-only.
   - New `PullRequest` fields must decode from v0.1.0 records (see M2's design
     constraints).

**Stretch:** an operator planning-guidance setting that adds owner text to the
discovery and consolidation prompts.

**Deferred:** rebasing onto a moved default branch. It changes which revision is
reviewed and verified. Such tasks keep blocking as `stale_base`.

## Release

1. Bump `VERSION` to `0.2.0` and add a dated `[0.2.0]` section to `CHANGELOG.md`.
2. Rehearse the upgrade: run a v0.1.0 compose stack with fixture work recorded,
   back it up, switch to the v0.2.0 images and confirm:
   - the state migrates;
   - the backup from M2 exists;
   - saved cycles, tasks and evidence still read back.
3. Tag `v0.2.0` and repeat M1's post-release checks.

## Acceptance criteria

1. Fixture e2e scenarios cover each new notification event, including a webhook
   delivery, and the new grounding fields reaching a planning prompt.
2. A v0.1.0 database with saved owned pull requests loads, migrates and plans on
   v0.2.0.
3. The upgrade rehearsal is recorded with versions, commands and results.
4. `make check` and `make test` pass, and so does the release workflow for
   `v0.2.0`.
5. Configuration, deployment and architecture docs describe the new events and
   grounding fields.

## Verification

- `SCENARIOS=notify make test-integration` and the planning scenarios touched by
  the grounding change.
- `make check` and `make test` before delivery.
- The release workflow run URL, the release URL and the rehearsal record.
